# Meeting notes research: notice a call, record it, write the notes (2026-10-14)

Scope: a new thing bots can do. Diego, in his words: "One of the options for what the agent can do is kind of like Whisper, where it detects when you're in a meeting and it pops up and says, do you want to record this meeting? And then the agents will be able to transcribe it… there should be the cute little agent on the very, very bottom of the screen that's kind of there so you can see when it's being transcribed."

"Whisper" is almost certainly **MacWhisper**, which does exactly this (section 1). The plan has three pieces: (1) a desktop companion app (Electron) that notices calls, asks "Want me to take notes?", shows the bot at the bottom of the screen while recording, and uploads audio; (2) a no-install recorder in the web app; (3) server-side transcription, then the bot writes notes and gets tools to read and search meetings.

This note is research plus Claude's recommendation (section 6). **Diego hasn't decided any of it.** It is not legal advice.

## 0. The answer on one screen

1. **Everyone detects a meeting the same way: "which app has the microphone open right now".** Granola, Otter, OpenWhispr and Anarlog all do this. Some add calendar events and app or process names. Nobody needs to listen to the audio to decide.
2. **Detection needs no scary permission.**
   - macOS: Core Audio's per-process objects (macOS 14+) say which app is using the mic. Read the app's bundle ID; no permission prompt.
   - Windows: WASAPI audio sessions on the capture devices give the process ID. The registry "ConsentStore" is a cross-check.
   - Linux: PulseAudio/PipeWire "source outputs".
3. **System audio from Electron 44** (the current stable, 44.7.2, published 2026-10-14):
   - **Windows:** `audio: 'loopback'` works.
   - **macOS 14.2+:** works since Electron 39 through Core Audio taps. It needs `NSAudioCaptureUsageDescription`. If the permission is missing, the track silently arrives already ended.
   - **Linux:** needs a Chromium flag that is off by default.
   - **On macOS, a tiny Swift helper using a Core Audio tap is the better choice.** It needs only the system-audio permission. Electron's path also needs Screen Recording, which macOS 15 re-asks about regularly.
4. **Token Factory has no speech-to-text.** The live model list on 2026-10-05 had 25 text, image and embedding models and nothing for audio. Included plans need another provider.
   - **Default:** Groq `whisper-large-v3-turbo` at about $0.04 per audio hour *(secondary)*. It speaks the OpenAI request shape and returns timestamps (`verbose_json`) for webm/ogg uploads.
   - **Fallback, and for speaker separation:** Together AI, with Parakeet v3 or Whisper plus `diarize`, at about $0.09/hour *(secondary)*.
5. **Cost per meeting-hour is pennies:**
   - Transcription is about $0.04–0.08 (two tracks, trimmed vs. untrimmed).
   - The notes call on Nemotron 3.5 Lightning is about $0.002.
   - So 50 hours a month (Pro) costs us about $2–4. The limits already in `plans.ts` (120 / 900 / 3,000 minutes) are affordable.
6. **Label speakers from the tracks, not with voiceprints.** Record the mic and the system audio as two tracks: mic = "You", system audio = "Others". Diarization within one meeting is optional (Speaker 1, 2…).
   - Never build cross-meeting voiceprints. A 2025 Illinois class action against Fireflies is about exactly that.
7. **Legal risk is real, and botless doesn't avoid it.**
   - Otter was sued in 2025 under federal and California wiretap law.
   - Granola, which is botless like our plan, was sued on 2026-07-30 on the same theory: "surreptitiously" recording participants.
   - About 10 states need every party's consent (California, Florida, Illinois, Maryland, Massachusetts, Montana, New Hampshire, Pennsylvania, Washington, Delaware *(disputed)*), plus hybrids.
   - What protects us: never auto-record, a visible bot, a one-tap "tell everyone" message, deleting audio after transcription, and no training on it.
8. **Diego's rule, "it only listens when it's visible on your screen", is enforceable in code** (section 6.10).
   - On the desktop, capture is tied to the floating window.
   - On the web, it's tied to the Document Picture-in-Picture window. Chrome/Edge 116+ and Firefox 151 have it; Safari doesn't. Sites can't choose where that window sits.

## 2. Noticing a meeting

### 2.1 The signal

"An app on the allowlist has had the microphone open for a few seconds." Then add context: the app's name, the calendar, and for browsers, a meeting URL or window title if readable. The two open-source desktop note-takers with this feature both work this way:
- **Anarlog:** Rust, MIT, about 9.5k stars. It used to be Hyprnote, then Char. Its detector crate is `crates/detect`.
- **OpenWhispr:** Electron 41, MIT, about 9.4k stars. It uses small native helpers in `resources/`.

Neither listens to audio to decide; Hedy's docs make the same promise, "never what is said" ([Hedy](https://hedy.ai/help/automatic-meeting-detection/), *secondary*).

### 2.2 macOS

**APIs (from the macOS 15.5 SDK header `AudioHardware.h`; the 13.3 SDK doesn't have them, the 14.5 SDK does):**
- `kAudioHardwarePropertyProcessObjectList` (`'prs#'`) on the system object: "an array of AudioObjectIDs that represent the Process objects for all client processes currently connected" to the audio system.
- On each process object:
  - `kAudioProcessPropertyIsRunningInput` (`'piri'`): 1 when "the process is running IO and there is at least one active input stream".
  - `kAudioProcessPropertyPID` (`'ppid'`) and `kAudioProcessPropertyBundleID` (`'pbid'`).
  - `kAudioProcessPropertyIsRunningOutput` (`'piro'`) and `kAudioProcessPropertyDevices` (`'pdv#'`) also exist.
- `kAudioDevicePropertyDeviceIsRunningSomewhere` on the default input device is a cheap "someone is using the mic" listener that works on older macOS too.
- Apple's online pages for these constants are bare; the header comments are the documentation.

**How the reference apps use them:**
- **Anarlog** listens to `DeviceIsRunningSomewhere` on the default input device (and re-attaches when the default device changes), then lists processes with `is_running_input`. It polls every second as a fallback.
  - It maps a helper process to the **outermost `.app` bundle**, so "Google Chrome Helper" becomes `com.google.Chrome`.
  - It labels Apple's call daemons (`/usr/libexec/avconferenced`, `com.apple.TelephonyUtilities.callservicesd`) as FaceTime or "iPhone Call".
  - It ignores its own process.
- **OpenWhispr's `macos-mic-listener.swift`** uses the same properties. On older systems it falls back to aggregate device activity (no app attribution).

**Meeting apps by bundle ID** (from Anarlog's `MEETING_APP_BUNDLES` and OpenWhispr's `BUNDLE_ID_MAP`):

**No permission is needed to detect.** Mic-in-use plus bundle ID covers it. Neither reference app asks for a permission to do this; we haven't confirmed it on a test machine (**UNVERIFIED**). The extras (titles, tabs, Zoom's mute state) each cost a permission prompt, so v1 skips them.

### 2.3 Windows

**First choice: WASAPI audio sessions.** Both reference apps use this, not the registry:
- Enumerate capture endpoints, then each one's `IAudioSessionManager2` → session enumerator → `IAudioSessionControl2`.
- Keep sessions in `AudioSessionStateActive`, defined as "at least one of the streams in the session is running".
- `GetProcessId` gives the PID; it returns `AUDCLNT_S_NO_SINGLE_PROCESS` when a session spans processes. Then map the PID to the process name.
- Anarlog polls this every second (`mic/windows.rs` calling `list/windows.rs`). OpenWhispr's `windows-mic-listener.c` is event-driven (`IAudioSessionNotification` plus `IAudioSessionEvents::OnStateChanged`).

**Second signal: the CapabilityAccessManager "ConsentStore" registry.**
- **Desktop (non-Store) apps:** `HKCU\Software\Microsoft\Windows\CurrentVersion\CapabilityAccessManager\ConsentStore\microphone\NonPackaged\<exe path with \ replaced by #>`. The HKLM copy is `HKLM\SOFTWARE\…\ConsentStore\<capability>\NonPackaged\*`.
- **Each entry holds** `LastUsedTimeStart` and `LastUsedTimeStop` as Windows FILETIMEs (the Velociraptor forensics artifact reads exactly these keys).
- **Store apps** sit directly under `…\ConsentStore\microphone\<PackageFamilyName>`, not under `NonPackaged`. A GitLab issue found Teams there, so walk the whole `microphone` key ([automattermostatus #17](https://gitlab.com/matclab/automattermostatus/-/issues/17), *secondary*). The new Teams' key name (`MSTeams_8wekyb3d8bbwe`) is **UNVERIFIED**.
- **"In use now"** = `LastUsedTimeStop == 0` with a nonzero start. This is community practice, not Microsoft documentation. Home Assistant users report values that stick ([thread](https://community.home-assistant.io/t/ha-desktop-companion/450755?page=14), *secondary*). Use it as a cross-check only.

**Window titles are free on Windows.** `GetWindowText` on another process's top-level window "retrieves the window caption text" with no permission ([Microsoft](https://github.com/MicrosoftDocs/sdk-api/blob/docs/sdk-api-src/content/winuser/nf-winuser-getwindowtextw.md)). So "Meet - abc-defg-hij - Google Chrome" can confirm a browser meeting.

Windows shows its own microphone icon in the taskbar notification area while any app uses the mic ([Microsoft support](https://support.microsoft.com/windows/privacy/windows-camera-microphone-and-privacy), *secondary*).

### 2.4 Linux

- **Signal:** PulseAudio "source outputs" (an app recording from an input). With PipeWire this works through pipewire-pulse.
- **How Anarlog does it** (`list/linux.rs`, `mic/linux.rs`):
  - subscribe to `SOURCE_OUTPUT` new, change and remove events;
  - list the source outputs, skip **corked** (paused) ones;
  - name the app from `application.name` or `application.process.binary`.
- **Without native code:** `pactl subscribe` plus `pactl list source-outputs` does the same thing. Whether `pactl` is installed on every distro is **UNVERIFIED**.
- **Process names:** OpenWhispr watches `zoom` and `teams`.

### 2.5 Calendar, and browser-only meetings

- **Calendar:** Build-a-bot already connects Google Calendar and Outlook. Copy Granola: if a call starts within about 15 minutes of an event with 2+ attendees, title the prompt with the event name, then pass the attendee names to the transcriber as spelling hints.
- **Meetings in a browser** (Meet, Teams web, Zoom web) show up as "Chrome is using the mic". Without permissions we can't tell Meet from a voice-search box.
  - macOS v1 says "Are you on a call in Chrome?", needs a longer sustain, and offers "Don't ask for Chrome".
  - Windows can read the window title.

## 3. Capturing the audio

### 3.1 Electron facts

- **Versions:** the current stable is **44.7.2**, published 2026-10-14 01:32 UTC; 43.7.11 and 42.11.14 are also maintained ([npm](https://registry.npmjs.org/electron), [releases](https://github.com/electron/electron/releases)). 45 is in beta (`45.0.0-beta.2`).
- **Electron 44.0.0** shipped Chromium 152.0.7977.54 and Node 24.18.1 ([release](https://github.com/electron/electron/releases/tag/v44.0.0)).
- **Supported OSes:** macOS 13 (Ventura) and up, Windows 10 and up, Linux x64/arm64 (the package README).
- **The API:**
  - `session.setDisplayMediaRequestHandler((request, callback) => callback({ video: source, audio: 'loopback' }))`.
  - `audio` can be `'loopback'`, `'loopbackWithMute'` or a `WebFrameMain` ([session.md](https://github.com/electron/electron/blob/main/docs/api/session.md)).
  - `getDisplayMedia` must still request video. Stop and remove the video track right away (electron-audio-loopback's README).
- **Never use `loopbackWithMute`.** In Chromium that device "will mute system audio during capturing" ([audio_device_description.h](https://github.com/chromium/chromium/blob/main/media/audio/audio_device_description.h)), so the user would stop hearing the meeting.
- **The docs disagree with each other:**
  - `session.md` still says loopback is "currently only supported on Windows".
  - `desktop-capturer.md` describes macOS 14.2+:
    - `NSAudioCaptureUsageDescription` is required. It belongs to the app that is responsible for the process; run from a terminal, that's the terminal.
    - Access sits behind the "System Audio Recording" privacy permission.
    - **"If the permission is missing or has been denied, `desktopCapturer` still produces an audio track, but it is created in the `ended` state and never delivers samples. No warning or error is surfaced to JavaScript."**
    - "Since Electron 39, Chromium uses the CoreAudio Tap API by default … There is no automatic fallback to the older ScreenCaptureKit-based … path", and the `MacCatapLoopbackAudioForScreenShare` flag no longer has any effect ([desktop-capturer.md](https://github.com/electron/electron/blob/main/docs/api/desktop-capturer.md)).
- **Chromium today** ([media_switches.cc](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc)):
  - **macOS:** the Core Audio tap path is used from macOS 14.2 (`MacOSVersion() >= 14'02'00`). The ScreenCaptureKit audio path is turned off on macOS 15.0+ "due to problems with permission prompt".
  - **Windows:** per-process loopback needs Windows 11.
  - **Linux:** screen-share loopback sits behind `PulseaudioLoopbackForScreenShare`, **disabled by default**.
- **Electron 44.0.0 fixed** `restrictOwnAudio` being ignored, which had let the app's own playback leak into loopback audio. Set it so the bot's sounds aren't recorded.
- **`electron-audio-loopback`** (MIT, v1.0.6, last published 2025-08-03) is **not needed on Electron 39+**, says its own README. It existed to set Chromium flags (`MacLoopbackAudioForScreenShare`, `PulseaudioLoopbackForScreenShare`, `MacSckSystemAudioLoopbackOverride`) for Electron 31–38. Its Linux trick (that flag) is still how to get loopback on Linux.

### 3.3 The mic track, and echo

- **Use headphones, or cancel echo.** Without headphones, the mic hears the other people through the speakers, and they show up twice ("You" and "Others").
- **Chromium may now remove that echo for us.** `kSystemLoopbackAsAecReference` is **enabled by default** in Chromium for Windows and macOS builds: "If echo cancellation for a mic signal is requested, use system loopback audio as reference signal to be able to cancel echo from all audio processes and not only audio from Chrome." It needs macOS 14.2+ or Windows 11 ([media_switches.cc](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc), [media_options.gni](https://github.com/chromium/chromium/blob/main/media/media_options.gni)).
  - So `getUserMedia({audio:{echoCancellation:true}})` in Electron may cancel Zoom's audio out of the mic. Whether Electron 44's Chromium 152 has it on is **UNVERIFIED**; test it.
- **Fallbacks:**
  - a dedupe pass that drops a "You" line when an overlapping "Others" line says the same thing. meeting-transcriber warns this can drop real quiet remarks, so it ships off by default;
  - an AEC helper (OpenWhispr's `native/meeting-aec-helper`, Anarlog's `crates/aec`).

### 3.4 The floating bot at the bottom of the screen (desktop)

Electron 44 typings and docs:
- **Position:** `screen.getPrimaryDisplay().workArea` (it leaves out the Dock and taskbar). Place a small frameless, transparent `BrowserWindow` at bottom-center, and re-place it on `display-metrics-changed`.
- **Staying on top:**
  - `setAlwaysOnTop(true, 'floating' | 'screen-saver')`; this is "not supported on Wayland".
  - `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true })` (macOS).
  - On macOS, `type: 'panel'`, which "enables the window to float on top of full-screened apps … and … appear on all spaces" ([base-window-options.md](https://github.com/electron/electron/blob/main/docs/api/structures/base-window-options.md)).
- **Focus:** `focusable: false` (on Windows it also implies `skipTaskbar`) and `showInactive()`, so the bot never steals focus mid-call.
- **Screen sharing:** don't call `setContentProtection(true)`. If the owner shares their screen, others then see the bot too, which is extra notice.

### 3.5 The no-install browser recorder

**Capture support** (MDN browser-compat-data, read from [GitHub](https://github.com/mdn/browser-compat-data)):
- Audio from `getDisplayMedia` exists in **Chrome/Edge 74+** only. Firefox and Safari don't capture audio at all.
- BCD's note: "On Windows and ChromeOS, the entire system audio can be captured when sharing an entire screen. On Linux and macOS, only the audio of a tab can be captured."
- That note is now stale for Mac. A tester found **Chrome 141+ on macOS 14.2+** offers system audio for a whole screen ([addpipe](https://blog.addpipe.com/getdisplaymedia-allows-capturing-the-screen-with-system-sounds-on-chrome-on-macos/), *secondary*). This matches Chromium's Core Audio tap code.

**Useful options** (Chrome versions): `systemAudio: 'include'` (105), `windowAudio` (141, partial), `preferCurrentTab` (94), `selfBrowserSurface` (112), `surfaceSwitching` (107), `monitorTypeSurfaces` (119).

**So:**
- A meeting in another **tab** (Meet, Teams web, Zoom web): share that tab with audio. This works on every desktop OS in Chrome and Edge.
- A meeting in the **Zoom or Teams app**: only Windows and ChromeOS (and Mac with Chrome 141+) can share system audio, through "Entire screen". Otherwise send people to the desktop app.

**The floating bot: Document Picture-in-Picture** (`documentPictureInPicture.requestWindow`):
- **Support:** Chrome/Edge 116+, **Firefox 151**, not Safari (BCD).
- **The spec** ([WICG](https://github.com/WICG/document-picture-in-picture/blob/main/spec.bs)):
  - It needs a user click ("transient activation").
  - "The PiP window will float on top of other windows" and "will never outlive the opening window".
  - **"The website cannot set the position of the PiP window."**
  - So the web bot can't be pinned to the bottom of the screen. The user drags it; the browser remembers where (`preferInitialWindowPlacement` from Chrome 130). Only the desktop app can do exactly what Diego described.

**Chunks** (the W3C MediaRecorder spec, read from [GitHub](https://github.com/w3c/mediacapture-record)): "When multiple Blobs are returned (because of timeslice or requestData()), **the individual Blobs need not be playable**, but the combination of all the Blobs from a completed recording MUST be playable." So upload `timeslice` chunks for safety, but transcribe only whole recordings:
- either stitch all chunks server-side,
- or **restart the MediaRecorder every few minutes** so each segment is a complete file. The length of the gap at a restart is **UNVERIFIED**; restart in a quiet moment.

### 3.6 Format and size

- Record each track as `audio/webm;codecs=opus`, mono, with `audioBitsPerSecond` around 24–32 kbps.
- By arithmetic, 32 kbps is about **14 MB per hour per track**, and a 5-minute segment is about 1.2 MB.
- That stays well under every provider's upload cap (Groq 25 MB, OpenAI 25 MB, Together 80 MB) and under OpenAI's reported 1,500-second limit for `gpt-4o-transcribe` (section 4).
- **webm, ogg and opus are accepted** by OpenAI and Groq (formats: flac, mp3, mp4, mpeg, mpga, m4a, ogg, wav, webm) and by Together (wav, mp3, m4a, webm, flac, ogg, opus, aac). This comes from the openai, groq-sdk and together-ai type definitions.

### 4.3 The request we'd send (Groq, Together, OpenAI `whisper-1`)

```
POST https://api.groq.com/openai/v1/audio/transcriptions        (Together: https://api.together.ai/v1/audio/transcriptions)
Authorization: Bearer <key>
Content-Type: multipart/form-data
  file=@seg-0007-others.webm   (filename with extension + audio/webm content type)
  model=whisper-large-v3-turbo  (Together: nvidia/parakeet-tdt-0.6b-v3 or openai/whisper-large-v3)
  response_format=verbose_json
  timestamp_granularities[]=segment
  language=en                   (optional; helps accuracy and latency)
  prompt=<meeting title + attendee names>   (Whisper only: spelling hints)
  diarize=true                  (Together only, for the "Others" track)
→ { text, segments: [{ start, end, text, … }] }   (groq-sdk's types declare only `text`; parse segments defensively)
```

Add each segment's start time to the chunk's start time to get the time within the meeting. Mistral is the same idea, with `diarize`, `context_bias` and `timestamp_granularities`, and without `response_format`.

### 4.7 Quality gotchas

- **Whisper makes things up over silence and pauses.** About 1% of transcripts contained invented phrases in a 2023 test, and longer non-speech stretches raised the rate ([Careless Whisper, FAccT '24](https://arxiv.org/html/2402.08021v2)). Trim silence (VAD) before upload; the mic track is mostly silence.
- **Mind the 10-second minimum and the rate limit.** Groq bills at least 10 seconds per request, and its free tier allows 7,200 audio-seconds an hour across the whole organization *(secondary)*. Send 2–5-minute segments, not single utterances. Queue them, and have a second provider ready.

## 5. Law and consent (US focus; not legal advice)

### 5.1 The baseline

- **Federal law is one-party.** Recording is lawful when "one of the parties to the communication has given prior consent", unless it's done for a criminal or tortious purpose: 18 U.S.C. § 2511(2)(d) ([LII](https://www.law.cornell.edu/uscode/text/18/2511), [9th Cir. memo](https://cdn.ca9.uscourts.gov/datastore/memoranda/2024/10/25/24-541.pdf), *secondary*).
- **State law can be stricter**, and federal law doesn't override it.

| Montana | Mont. Code Ann. § 45-8-213 | Notice to all parties |

**Hybrids:**
- **Connecticut:** all parties for phone calls under civil law (§ 52-570d).
- **Nevada:** phone calls (NRS 200.620) are treated as all-party.
- **Oregon:** all parties for **in-person** talk (ORS 165.540); one party for phone calls.

- [RCFP guide](https://www.rcfp.org/introduction-to-reporters-recording-guide/), [RCFP California](https://www.rcfp.org/reporters-recording-guide/california/), [MWL chart](https://www.mwl-law.com/wp-content/uploads/2018/02/RECORDING-CONVERSATIONS-CHART.pdf), [layer3labs list](https://www.layer3labs.io/guides/two-party-consent-states), all *(secondary)*.
- Counts run from 9 to 12 depending on the hybrids. Check each statute on the official site before relying on it.

### 5.3 Calls that cross state lines

- **Practical rule:** a video call with anyone in an all-party state needs everyone's consent.
- **The leading case:** in *Kearney v. Salomon Smith Barney* (Cal. 2006), California's all-party rule was applied to calls recorded in Georgia (a one-party state) with Californians on the line ([SCOCAL](https://scocal.stanford.edu/opinion/kearney-v-salomon-smith-barney-33656), [Littler](https://www.littler.com/news-analysis/asap/californias-supreme-court-requires-employers-nationally-re-examine-telephone), *secondary*).
- **It likely reaches video calls.** Commentators read California's rule as covering confidential video calls, including someone dialing into Zoom from a cell phone ([RCFP California](https://www.rcfp.org/reporters-recording-guide/california/), *secondary*).
- **We can't know where everyone is**, so the product has to assume all-party.

### 5.4 Lawsuits against AI note-takers

1. **In re Otter.AI Privacy Litigation (N.D. Cal.).**
   - *Brewer v. Otter.ai*, No. 5:25-cv-06911, was filed 2025-08-15; the cases were consolidated 2025-10-22.
   - **The allegation:** Otter Notetaker asks the **host** for consent, but by default not the other attendees; it records non-users, and Otter trains on the recordings.
   - **The claims:** the federal wiretap law (ECPA), California's privacy law (CIPA §§ 631, 632, 635, 638.50), the computer-fraud act (CFAA), intrusion and conversion, plus Illinois and Washington law.
   - **Status:** a motion to dismiss is pending, with no ruling found ([Fisher Phillips](https://www.fisherphillips.com/en/news-insights/new-lawsuit-highlights-concerns-about-ai-notetakers.html), [IAPP](https://iapp.org/news/a/dressing-old-laws-in-class-action-suits-applying-anti-wiretapping-laws-to-ai-transcription-services), [UC Today](https://www.uctoday.com/security-compliance-risk/otter-ai-on-trial-and-the-ai-notetaker-industry-with-it/), *secondary*).
2. **Cruz v. Fireflies.AI (C.D. Ill. 3:25-cv-03399, filed 2025-12-18).**
   - **BIPA:** the claim is that "speaker identification" builds **voiceprints** of non-users without written consent or a published retention policy.
   - **Damages:** BIPA sets $1,000 or $5,000 per violation ([complaint](https://www.workplaceprivacyreport.com/wp-content/uploads/sites/938/2026/04/Fireflies.ai-Complaint-1.pdf), [summary](https://www.dataprivacyandsecurityinsider.com/2025/12/lawsuit-alleges-fireflies-ai-corp-illegally-collects-biometric-data-from-virtual-meetings/), *secondary*).
3. **Chamberlain v. Granola (N.D. Cal. 3:26-cv-07926, filed 2026-07-30).** This is against a **botless** product like ours.
   - **The allegation:** Granola "surreptitiously intercepts, records, and interprets the communications of every participant … without their knowledge or consent", and trained AI on the content.
   - **The claims:** ECPA, CIPA §§ 631/632, CDAFA, intrusion, UCL, unjust enrichment.
   - **Status:** no answer or ruling yet ([complaint](https://storage.courtlistener.com/recap/gov.uscourts.cand.475308/gov.uscourts.cand.475308.1.0.pdf), [PPC Land](https://ppc.land/granola-sued-for-recording-meetings-without-consent-to-train-ai-models/), *secondary*).

**The lesson:** being botless isn't a defense. The facts that matter are whether everyone knew, whether anyone said no, and what happened to the audio (training).

### 5.5 What lowers the risk

- **Never record silently.** No auto-record in v1; every recording starts with the owner's tap.
- **Tell everyone, and make it easy:**
  - a one-tap message in the meeting chat (Granola's pattern);
  - the owner saying it out loud;
  - optionally a line in the calendar invite.
- **Make it visible.** The bot sits on screen for the whole recording; the OS's own dots and icons also show.
- **Make stopping easy.** "Stop and delete" removes everything captured so far.
- **Keep text, not audio.** Delete the audio after transcription. Never train on users' meetings. Publish how long we keep things.
- **No voiceprints.** Speaker labels come from the tracks; any diarization stays within one meeting, and nothing is stored to recognize people later (avoids the BIPA theory).
- **Ask again every time.** One "Take notes" tap per meeting, with a reminder of the consent duty the first time.
- **Skip phone calls in v1:** FaceTime, and iPhone calls relayed to the Mac. That avoids § 632.7 for now.

### 5.6 Apple's precedent: iPhone call recording (iOS 18.1+)

- **Everyone hears it:** "both call participants hear an audio notice that the call is being recorded" ([Apple](https://support.apple.com/en-us/121583), *secondary*).
- **It repeats:** the personal-safety guide says the notice replays periodically during the call, and asks users to get explicit consent ([Apple](https://support.apple.com/guide/personal-safety/ipsfa513e1a6/web), *secondary*).
- **Not offered everywhere:** call recording isn't available in the EU and a few other countries *(secondary)*.
- **The bar it sets:** audible notice to every participant. A desktop app can't inject audio into Zoom without a virtual mic, so the chat message plus the owner saying it is the practical equivalent.

### 5.7 EU / GDPR, briefly

- **A lawful basis is needed before recording** (Art. 6). The host's consent isn't the other participants' consent. In workplaces, consent is often invalid because of the power imbalance, and works councils (Germany, France) may need to be consulted.
- **Notice:** Art. 13/14 transparency means telling people before recording.
- **Voice becomes sensitive data under Art. 9 when processed to identify someone** (voiceprints or speaker identification); plain transcription usually isn't.
- **Contracts don't shift blame:** a processor agreement (DPA) doesn't move responsibility off the controller.
- Sources: [Mayer Brown 2026](https://www.mayerbrown.com/de/insights/publications/2026/06/ai-notetakers-productivity-tool-or-emerging-legal-risk), [Hedy GDPR checklist](https://www.hedy.ai/post/gdpr-checklist-ai-meeting-tools), *secondary*; no EDPB guidance specific to note-takers was found. Apple not offering call recording in the EU is a hint.
- **Suggestion:** launch meetings in the US first, and add an EU-specific notice later.

## 6. Recommendation for Build-a-bot v1 (Claude's; Diego to decide)

### 6.1 Detection, per OS

The desktop app runs one small native helper per OS. It prints JSON events: `{type:"mic", app, bundleOrExe, pid, active}`.

- **macOS: a Swift helper.**
  - Listen to `kAudioDevicePropertyDeviceIsRunningSomewhere` on the default input device (and re-attach when the default changes).
  - On change, read `kAudioHardwarePropertyProcessObjectList`. For each process with `kAudioProcessPropertyIsRunningInput == 1`, take `kAudioProcessPropertyPID` and `kAudioProcessPropertyBundleID`, then map to the outermost `.app`.
  - Match against the bundle-ID table in 2.2.
  - **No permissions.** No titles or AppleScript in v1.
- **Windows: a C or Rust helper.**
  - Use WASAPI sessions on every capture endpoint: `IAudioSessionManager2` → active sessions → `GetProcessId` → exe name.
  - Make it event-driven, or poll every second.
  - Confirm browsers by window title (`GetWindowText`: "Meet - …", "| Microsoft Teams", "Zoom Meeting").
  - Cross-check with ConsentStore `LastUsedTimeStop == 0`.
- **Linux:** `pactl subscribe` plus `pactl list source-outputs` (not corked) → `application.process.binary`. Linux ships after Mac and Windows.
- **Rules for every OS:**
  - ignore our own process;
  - meeting apps only (allowlist);
  - **at least 5 s of sustained mic use** for native apps and **15 s for browsers**;
  - one prompt per call;
  - a 5-minute cooldown after "Not now" (OpenWhispr has a 5-minute cooldown constant);
  - "Don't ask for this app" per app (MacWhisper's).
- **Calendar:** a server-side match within ±15 minutes of an event with 2+ attendees gives the prompt its title and the transcriber's spelling hints.
- **Buy-instead fallback:** Recall's Desktop SDK (Mac and Windows) at about $0.50–0.65 per hour.

### 6.2 Capture

**Two tracks, always:** the mic ("You") and the system audio ("Others"). Each goes through its own MediaRecorder (`audio/webm;codecs=opus`, mono, about 32 kbps), restarted every 5 minutes so each segment is a complete file. Upload each segment as it finishes (signed URL → temporary storage).

| | Mic | System audio |
|---|---|---|
| macOS 14.2+ | `getUserMedia` with `echoCancellation: true` | **The Swift helper's Core Audio tap** (AudioTee-style, excluding our own PID) → PCM → AudioWorklet → MediaRecorder. It needs only `NSAudioCaptureUsageDescription` and the system-audio permission. Fallback: Electron `'loopback'` (needs Screen Recording) |
| macOS 13–14.1 | Same | Electron `'loopback'` (the ScreenCaptureKit path), or mic-only. Few users |
| Windows 10/11 | Same | Electron `'loopback'` with `restrictOwnAudio`; or a helper using process loopback that excludes us (Windows 10 build 20348+) |
| Linux (later) | Same | `PulseaudioLoopbackForScreenShare` + `'loopback'`, or a monitor-source helper |
| Browser | `getUserMedia` | Tab audio from `getDisplayMedia` (any OS, Chrome/Edge); "Entire screen" system audio on Windows and ChromeOS (and Mac with Chrome 141+) |

**Package and sign it:**
- Code-sign and notarize the Mac app; the Apple Developer Program is 99 USD a year ([Apple](https://developer.apple.com/programs/whats-included/)).
- Put `NSAudioCaptureUsageDescription` and `NSMicrophoneUsageDescription` in the **main** app's Info.plist. macOS attributes permission to the responsible app.
- Watch for the "ended" audio track: Electron gives no error when the permission was denied.
- **Merge with the Bridge.** The existing Bridge (`bridge/`) already runs on the user's computer. The meetings app can become "the Build-a-bot app", hosting both, so people install one thing.

### 6.3 Default transcription provider (included plans)

- **Nebius can't do it** (4.1).
- **Default: Groq `whisper-large-v3-turbo`.**
  - $0.04 per audio hour *(secondary)*, OpenAI-shaped, segment timestamps, webm/ogg accepted.
  - Fast: 216× real time, per Groq *(secondary)*.
  - Groq is already in our own-key list.
  - Before launch, get paid-tier rate limits; the free tier is 7,200 audio-s/hour per organization.
- **Second provider and diarization: Together AI.**
  - `nvidia/parakeet-tdt-0.6b-v3` or `openai/whisper-large-v3`, $0.09 an hour *(secondary)*.
  - `diarize: true` for the "Others" track when there are 3+ people.
  - Used automatically when Groq rate-limits or fails.
- **Own keys:** if the owner's brain uses their own OpenAI, Groq, Mistral or Together key, transcribe on their key (it doesn't count against our minutes).
- **Not for included plans:** OpenAI's `gpt-4o-transcribe*` returns no timestamps except the diarize variant, and costs 4–9× more.
- **Before launch, check each provider's data-retention and training terms** (not checked here).

### 6.4 On-device transcription: not in v1; v1.1 as "Transcribe on this computer"

- **Why not v1:** a model download of hundreds of MB, CPU and battery load during calls, and three OSes to test.
- **Why soon after:** it's the strongest privacy story (audio never leaves the computer) and costs us $0. It also fits the Bridge crowd.
- **Path:** sherpa-onnx-node (Apache-2.0, prebuilt for mac/win/linux) with Parakeet TDT 0.6B v3 int8 (CC-BY-4.0, so add an attribution line in About) and its offline diarization. FluidAudio or WhisperKit are better on Macs if we go native.

### 6.5 Speaker labels

- **"You"** is the mic track, labeled with the owner's name. **"Others"** is the system track. Merge the two by time.
- **Optional:** diarize the "Others" track into "Speaker 1, 2…" within the meeting. Let the notes model *suggest* names from context ("thanks, Priya"), shown as suggestions the owner can rename.
- **In-person meetings** (mic only) are labeled "Room", optionally diarized.
- **No voiceprints, and no "recognize Priya next time".** BIPA (5.4) and GDPR Art. 9 (5.7) both point this way.
- **Echo:** rely on Chromium's echo canceller (3.3). If that fails, flag "You" lines that duplicate "Others" lines rather than silently dropping them.

### 6.6 What we store, and for how long

| Data | Keep | Why |
|---|---|---|
| Audio segments | Until transcribed. **Delete right after; never more than 24 h** (retries). Never used for training | The Granola and Jamie pattern; limits what a breach exposes; lowers wiretap and BIPA exposure |
| Transcript (segments with timestamps and track) | **90 days by default**, with settings: 30 days, forever, or "delete now, keep the notes" | Needed to search, re-summarize and quote. Granola keeps transcripts for regeneration |
| Notes (summary, decisions, action items) | Until the owner deletes them | They're the owner's notes |
| Meeting record: app, title, start and end, **consent confirmations** (who tapped, when, whether a notice was sent) | With the notes | Proof that we asked |
| Voiceprints / embeddings | **Never stored** | BIPA |

Account export and delete (already built) must include meetings. Transcripts are untrusted text from other people: anyone on a call can say "ignore your instructions…". So meeting tools **taint the run** like `web_browse` does today, and actions planned from a transcript go through the normal approval rules.

### 6.9 Consent copy (the bot is talking, so use the bot's name)

**First time only.** A sheet, which the owner must acknowledge:

> Some places, like California, Florida, Illinois, Pennsylvania and Washington, require **everyone** on a call to agree to being recorded. I'll help you tell them.
> I only listen while I'm on your screen. I delete the audio once your notes are written, and I never use your meetings to train AI.
> ☐ I'll let people know when I'm using Blip to take notes.   **[Got it]**

**The pop-up** (bottom of the screen, the bot's face; it hides itself after 15 s):
> 👋 Looks like you're on a **Zoom** call (*Design sync*). Want me to take notes?
> **[Take notes]**   [Not now]   ⋯ (Don't ask for Zoom)
> *Only if everyone's OK with it. I can post a heads-up in the chat.*

**After "Take notes":** offer the heads-up, with one tap to copy it and paste into the meeting chat:
> Heads-up: I'm using my assistant Blip to take notes on this call (a transcript and a summary). Let me know if you'd rather I didn't.

**While recording** (the floating bot, with a soft "listening" animation):
> **Blip is taking notes · 12:04**   [Pause] [Stop]

**When someone objects:** "Stop and delete" removes everything captured so far.

**Finished:**
> Notes are ready: 3 decisions, 5 action items. **I deleted the audio.**

**The browser** shows the same flow inside the PiP window. Chrome's own "sharing this tab" bar and picker are an extra, unskippable consent step.

### 6.10 "It only listens when it's visible on your screen" in code

1. **The window comes first.** The capture pipeline can't start until the floating bot window has emitted `show` and reports `isVisible() && !isMinimized()`.
2. **Checked every second, and on events.** If the window is hidden, closed, minimized or moved fully off-screen, if the display sleeps or the screen locks (`powerMonitor` `lock-screen`, `suspend`), or if the user quits: **stop and finalize.**
3. **No "hide while recording" setting, ever.** The bot can be dragged, but snaps back inside `workArea`. No click-through mode, and no content protection. *(Changed 2026-10-20 at Diego's request: the owner can hide the bot for a screen share while the menu-bar or tray icon shows it's still listening. See DECISIONS.md.)*
4. **Nothing before the tap.** Detection reads only "who has the mic" (metadata); we never buffer audio before "Take notes". Krisp discards anything recorded before its bot is invited; we never record it at all.
5. **No auto-record setting in v1.** If one is ever added, it would require the calendar-invite notice and stay off by default.
6. **The web recorder only runs while its PiP window is open.** The PiP window's `pagehide` stops recording; closing the opener tab closes the PiP (spec).
   - Browsers without Document PiP (Safari, older Firefox) get "Use Chrome or the desktop app". Firefox 151+ can do mic-only (in-person) meetings.
7. **The OS says it too:** macOS shows the orange (mic) and purple (system audio) dots, and Windows shows its mic icon. Our UI never fights or hides them.
